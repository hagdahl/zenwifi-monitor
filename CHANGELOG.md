# Changelog

## 0.1.0 - Unreleased

### Added

- Closed F7 and F8: a restart now requires evidence rather than the age of a marker. The decision was the age of `first_failure_utc`, which only a successful run cleared, so nothing required a run to have happened in between. Any gap in monitoring — a sleeping machine, a logged-off user, a run that declined the lease — turned a stale marker into a restart on the first failed probe afterwards, on evidence of roughly no outage, while the event text and the notice both asserted fifteen minutes. The decision is now computed from the `runs` table, which already records every run and its connectivity result, and needs two independent conditions: the most recent successful run at least `failure_minutes_before_reboot` old, and at least `monitor.required_failed_runs` failed runs inside `monitor.failure_window_minutes`. The owner proposed three failures in thirty minutes, which closes the staleness directly; the duration condition was added alongside it because the count alone would fire after ten minutes and quietly weaken the documented fifteen. `required_failed_runs` is floored at two in validation so no configuration can restore the single-observation behaviour, and flapping no longer counts, because one successful run moves the reference forward. F8 dissolved rather than needing its own fix: the marker is no longer a decision input, so one left behind by a partial failure can cause at most a duplicate log line; it is also cleared before the work that can fail and committed with the recovery event. The event detail and the notice now state the observed duration and the number of failed checks instead of a constant, which also closes one F17 item. `positive_int` moved from `src/health.py` to `src/_defaults.py` rather than being duplicated, since a second declaration of a shared rule is the drift this project has already been bitten by. Recorded as ADR-023. Affected: `src/watchdog.py`, `src/_defaults.py`, `src/health.py`, `04_tests/test_watchdog.py`, `config.example.json`, `00_admin/DECISIONS.md`, `01_docs/IMPROVEMENT_PLAN.md`, `01_docs/REMEDIATION.md`. The suite was rewritten as F15 requires: the offline cases drive `main()` repeatedly so the run history is written by the code under test and only the recorded timestamps are moved, instead of seeding the value the code is supposed to derive. Four pins were checked by reverting the fix and confirming the suite fails, two of which were blind before this change: removing the evidence condition, removing the duration condition, reading the failure window where the cooldown belongs, and not clearing the announcement marker on recovery. The cooldown case now probes at twenty minutes, between the two thresholds, where zero and forty-five fell the same side of both. New cases pin that a single observation after a nine-hour gap decides nothing and that a successful run between failures resets the duration. All eight suites exit 0 on Linux and on Windows. The live configuration was migrated to carry the two new keys, validated against the monitor's own predicate, and a scheduled run then completed normally. - Recorded the fourth independent review round. Five reviewers examined the published commit `178adf4` with one lens each and no knowledge of the implementation reasoning: safety controls, security and release hygiene, documentation accuracy, test quality, and concurrency. The test-quality reviewer worked by mutation, applying forty deliberate defects and recording which ones the suites failed to catch. The report is `01_docs/REVIEW_178adf4.md`, in the format `01_docs/INDEPENDENT_REVIEW_PROMPT.md` prescribes, and it separates findings that were reproduced by executing the failure from findings established only by reading, because the first are facts and the second are arguments. Eleven findings are carried into section 9 of the improvement plan as F7 to F17. The most serious, reproduced: the restart decision measures the age of a stored marker rather than an observed outage, so any gap in monitoring — a machine asleep, a user logged off, a run that declined the lease — turns a stale marker into a restart on the first failed probe afterwards, on evidence of roughly no outage at all, while the event detail and the notice both assert fifteen minutes. Verdict: ready with changes for public publication, not ready for production activation until F7 and F8 are closed. The owner has been informed and has chosen to leave production execution enabled pending the fix; that acceptance is recorded in the report rather than left implicit. This entry also corrects two occurrences of "all nine suites" in earlier entries, which the review caught: there are eight. Affected: `01_docs/REVIEW_178adf4.md`, `01_docs/IMPROVEMENT_PLAN.md`, `CHANGELOG.md`. No source file changed, so no behaviour changed and the suites are unaffected. - Made two monitoring runs impossible to overlap, and closed the bookkeeping the last few commits left behind. The silent launcher returns before its child, so the scheduled task reads as finished while the run is still going and the next trigger starts a second one. Two concurrent runs would each drain the outbox, and an event delivered by both would reach Notion twice. An exclusive lease row in SQLite now decides who runs: it is taken before any monitoring work and released in a `finally`, so an early return, an exception and a normal end all release it on the same path, and release is owner-scoped so a slow run whose lease was stolen cannot delete the new owner's. A lease older than `monitor.run_lease_minutes`, default ten, is taken over, because a lock a killed run holds for ever would replace double delivery with no monitoring at all. A run that finds the lease held records a skip and exits zero, since the run holding it is doing the work. The `--reset-outbox-attempts` branch takes the lease too, and says out loud that it changed nothing rather than returning a silent zero.
