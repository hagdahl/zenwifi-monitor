# Decisions and assumptions

| ID | Date | Status | Decision or assumption | Rationale |
|---|---|---|---|---|
| ADR-001 | 2026-07-26 | Approved | Project logic is stored in the project root and operations logs/state use a separate, locally configured path outside the project tree. | Logs must remain available during an Internet outage. |
| ADR-002 | 2026-07-26 | Approved | Windows Credential Manager stores router and Notion secrets. | Secrets must not be stored in code, configuration files, or logs. |
| ADR-003 | 2026-07-26 | Approved | Router restart and Notion writes are allowed only with explicit `--execute`, every five minutes, after 15 continuous failure minutes and with a 30-minute cooldown. Authorization remains valid until revoked by the project owner. | Standing authorization under A1. The content of a Notion write is governed by ADR-014, which records that technical error detail is not minimized. |
| ADR-004 | 2026-07-26 | Superseded by ADR-010 | Tests, dry-run, and the current scheduled task must never request a router restart. | Independent safety boundary requested by the project owner. |
| ADR-005 | 2026-07-26 | Approved | The scheduled task runs only under the project owner's logged-in Windows account. | The same user profile can read Credential Manager and display a persistent restart notification. |
| ADR-006 | 2026-07-26 | Approved | Local SQLite logging is mandatory; Notion logging is an opt-in secondary destination. | Monitoring must preserve local operational evidence during Internet outages and must not depend on a remote integration. |
| ADR-007 | 2026-07-26 | Approved | ZenWiFi Monitor is published under Apache License 2.0 with David Hagdahl as the copyright owner. | The license permits broad reuse with an express patent grant and aligns with the Apache-2.0 router-library dependency. |
| ADR-008 | 2026-07-26 | Approved | Local configuration schema migrations are dry-run-first, create an ignored backup before writing, preserve TLS, and require an explicit opt-in for Notion logging. | Migration must not activate external behavior or silently change optional remote logging. |
| ADR-009 | 2026-07-26 | Approved | Public release uses an ignored, history-free `_public` staging tree generated only from a clean current source tree. | Earlier local Git history contains environment-specific and personal metadata that must never reach the public remote. |
| ADR-010 | 2026-07-27 | Approved | Production activation requires a separate owner decision, task registration with `-EnableExecution`, and local `execution_mode` set to `execute`. Tests and dry-run must never request a router restart. | The explicit task argument and local configuration are independent activation gates. |
| ADR-011 | 2026-07-27 | Approved | The project carries a single semantic version in the root `VERSION` file. Every tracked file except `LICENSE` and `VERSION` carries a `ZenWiFi Monitor version: MAJOR.MINOR.PATCH` marker in its native comment syntax; `config.example.json` carries it as a `config_version` key. `scripts/check_versions.py` verifies that all markers and the newest `CHANGELOG.md` release heading equal `VERSION`, and CI fails on drift. Alternatives considered: independent per-file versions, rejected because Git already provides per-file history and per-file counters drift silently; a project version plus per-file revision counters, rejected as unjustified maintenance for a single-maintainer project. Consequence: a release bumps `VERSION`, the CHANGELOG heading and every marker together. | The governing standard prescribes no versioning scheme for downstream projects, so the scheme is a project decision. A single version keeps the marker verifiable mechanically and mirrors how the standard marks its own documents. |
| ADR-012 | 2026-07-27 | Approved | Every scheduled ZenWiFi Monitor job is registered through `scripts/RouterWatchdog.vbs`, which launches the target script with window mode 0 and without waiting. The wrapper takes `--script=<entry point>` so additional jobs reuse one silent launcher, but only against a two-entry whitelist, `src\watchdog.py` and `src\health.py`; any other value, and any argument the wrapper does not recognise, exits 2 so Task Scheduler records the refusal and the wrapper cannot become a general silent runner for an arbitrary file, and `Install.ps1` refuses to report success unless the registered task action is `wscript.exe`. Notices are spawned through the windowless interpreter with `CREATE_NO_WINDOW`. The wrapper resolves the interpreter from `%LOCALAPPDATA%\ZenWiFiMonitor\.venv` first and the project tree second, and refuses rather than launching what is not there: exit 3 when no interpreter is found and exit 4 when the entry point is missing. Every refusal is also appended to the bootstrap error log, because an exit code alone is invisible unless somebody reads the task history. Alternatives considered: one wrapper per job, rejected as duplicated launch logic that drifts; registering `python.exe` directly, rejected because it raises a console window and breaks silent operation; calling `Run` without checking the paths first, rejected because `Run` in window mode 0 without waiting reports no error, so a missing interpreter leaves the job dead while Task Scheduler reports success. | An unattended job must raise no UI surface, steal no focus, and still leave a durable run marker. A single audited wrapper makes that property verifiable for every present and future job. |
| ADR-013 | 2026-07-27 | Approved | Notion delivery runs through a durable SQLite outbox: an event is committed locally before any remote call and marked delivered only after a successful response; undelivered events are sent oldest first and delivery stops on the first failure. Retries are bounded per event and per run, delivered events are purged after a retention window, and persisted error detail is sanitized so no authorization header is stored. A separate standard-library health monitor runs on its own fifteen-minute silent task, reports a stale run, an unreadable database, a changed bootstrap log and a stalled outbox, notifies only on a new or escalating unhealthy state, and can never restart the router. Bootstrap logging is size-bounded with rotation before write. Alternatives considered: delivering inline at event creation, rejected because an outage is exactly when the remote call cannot succeed; unbounded retry, rejected because one poison event would block the queue forever. | Local operational evidence must survive an outage and reach Notion afterwards at least once, and silent monitoring needs an independent observer that does not share the watchdog's dependencies. Delivery is deliberately at-least-once rather than exactly-once: a run interrupted between a successful response and the delivered mark resends the event, which is preferred over dropping it. |
| ADR-014 | 2026-07-27 | Approved | Technical error detail delivered to Notion is not content-minimized. An `Error` event carries the unmodified exception text, which can include the router endpoint and other environment data. The project owner accepts this because the configured Notion data source is a private surface reachable only by the owner's own integration, and because the alternative, discarding error text, would remove the evidence the remote log exists to preserve. Credentials remain excluded: no token, password or authorization header is ever placed in an event. Alternatives considered: a fixed error template with only the exception class, rejected as losing the diagnostic value; local-only error events, rejected because a failed restart is exactly the event worth mirroring. Consequence: an operator pointing this project at a shared or team Notion database inherits a different risk and should minimize the detail first. | The risk depends on who can read the destination, and the owner's destination is private. Recording the acceptance keeps the documented data classification honest. |
| ADR-015 | 2026-07-27 | Approved | The repository deviates from the standard's B9 tree. Source lives in `src/` and `scripts/` rather than `03_src/modules` and `03_src/scripts`, and `02_data/`, `05_logs/` and `06_exports/` do not exist. B9 states that the structure shall be adapted to the project type and that any deviation is recorded here. This project is a single-purpose watchdog with three source modules and no data pipeline: it ingests nothing, produces no exports, and writes its only persistent state to a SQLite database and log directory that ADR-001 deliberately places outside the project tree so they survive an outage. Creating empty `02_data/`, `05_logs/` and `06_exports/` directories would therefore describe a pipeline that does not exist and would invite writable runtime data back into a cloud-synced tree. Alternatives considered: adopting the full tree, rejected for the reasons above; renaming `src/` to `03_src/` alone, rejected because it would break the registered scheduled task's launcher path and every documented command for a purely cosmetic gain, with no `03_src/modules` split to justify it at three modules. Consequence: a contributor arriving from the standard will not find the numbered source directory; `01_docs/ARCHITECTURE.md` carries the mapping, the edit status per directory and the logic/data classification. Revisit if the project grows a data pipeline or a fourth source module. | The layout is verified against an actual filesystem inventory rather than a template, and the deviation is deliberate and bounded rather than accidental drift. |
| ADR-016 | 2026-07-27 | Approved | The Python environment the scheduled jobs use lives at `%LOCALAPPDATA%\ZenWiFiMonitor\.venv`, beside the bootstrap log, not in the project tree. The project tree is cloud-synced, and a sync or folder-hygiene routine moved the project-local `.venv` out from under the running jobs, after which the launcher called `Run` on a path that no longer existed; the job died while Task Scheduler reported success, and the first failure left an invisible script-host dialog that wedged the task so every later run was refused by the single-instance policy. A project-local environment remains supported as a fallback for development. Alternatives considered: keeping the environment in the project and excluding it from sync, rejected because it depends on a setting outside this project that no test can assert; moving the whole repository off the synced drive, rejected as a larger change than the failure requires and still leaving the environment inside a working tree that gets cleaned. Consequence: `Install.ps1 -InstallDependencies` creates the environment in the runtime location, and the documented commands name it. | This is the same reasoning ADR-001 applies to the database and the logs: state an unattended job depends on must not live where another tool may move it. |
| ADR-017 | 2026-07-27 | Approved | Dependencies are locked by hash, not only by version. `requirements.in` names the direct dependencies and is the only file edited by hand; `requirements.lock.txt` is the generated, fully resolved output carrying every transitive distribution with its hashes, and is installed with `--require-hashes` so pip refuses the entire set unless every artefact matches. One file covers both supported platforms through environment markers rather than a file per platform. GitHub Actions are pinned to immutable commit hashes with the upstream release name recorded beside each. Alternatives considered: version pins alone, rejected because a version pin does not detect a substituted artefact; a lock file per platform, rejected as two files that drift; leaving actions on moving tags, rejected because a retagged release enters the build silently. Consequence: adding or upgrading a dependency means regenerating the lock file and committing input and output together. | An unattended job that can restart a router should fail its install rather than run an artefact nobody verified. |
| ADR-018 | 2026-07-27 | Approved | Exactly two behaviours may branch on the operating system, and both live behind `src/_platform.py`: showing a notice to whoever is at the machine, and starting a detached child without raising a window. The credential rule lives behind `src/_secrets.py`, which names the one acceptable keyring backend per platform and refuses every fallback, so a plaintext or in-memory store cannot satisfy the code while breaking the rule. `_platform.py` is standard-library-only, which is what lets the independent health monitor share it without inheriting the watchdog's dependencies; `_secrets.py` imports keyring inside its functions so the core stays importable, and its suites runnable, where the dependency or a backend is absent, without ever letting a real run proceed on an unacceptable store. A notice is best effort and never raises, and is always shown from a detached child rather than inline, because a message box is modal and an unattended job that shows one inline never exits. `04_tests/test_platform.py` asserts statically that no other module names a platform primitive, so a later edit cannot quietly re-split the platforms. Alternatives considered: one adapter class per platform selected at import, rejected as ceremony for two functions; keeping the branches inline with `sys.platform` tests, rejected because they were already duplicated between the two entry points and drifted; putting the secret store in the same module, rejected because it would give the standard-library-only health monitor a third-party dependency. Consequence: adding a platform means adding one backend name and one notice implementation, and the static assertion tells a contributor where. | The restart gates and the SQLite schema are the safety-relevant core and must read identically on every platform. Isolating the two genuinely platform-specific behaviours is what keeps that core reviewable as one thing. |
| ADR-019 | 2026-07-27 | Approved | One monitoring run at a time is enforced by the application, through an exclusive lease row in SQLite, not by the scheduler. The silent launcher returns before its child, so the task reads as finished while the run is still going and the next trigger starts a second one; two concurrent runs would each drain the outbox and an event delivered by both would be delivered twice. The lease is taken before any monitoring work and released in a `finally`, so an early return, an exception and a normal end all release it on one path; release is owner-scoped so a slow run whose lease was stolen cannot delete the new owner's. A lease older than `monitor.run_lease_minutes`, default ten, is taken over, because a lock a killed run holds for ever would replace double delivery with no monitoring at all, and an unparseable timestamp counts as stale for the same reason. A run that finds the lease held records a skip and exits zero: the run holding it is doing the work, so that is a correct outcome and not an error. The launcher still discards the child's exit code, deliberately: making it wait would let one hung run block every later trigger, and a failed run is already visible as a missing `runs` row that the health monitor reports. Alternatives considered: a per-row delivery claim, rejected as subsumed by the lease and as protection for only one of the two harms; making the launcher wait and propagate the exit code, rejected because it converts a hang into a permanent stop; relying on the scheduler's single-instance policy, rejected because it is what already failed and it does not exist under `systemd` in the same form. | The overlap is a property of the application, so the guard belongs in the application, where it is testable and where it carries to the next platform unchanged. |
| ADR-020 | 2026-07-27 | Approved | The Debian deployment uses two `systemd` oneshot services with their own timers, a dedicated `zenwifi` system account with no login shell, and encrypted `systemd` credentials as the secret source. A service has no desktop keyring, so `src/_secrets.py` selects the credential source by the presence of `CREDENTIALS_DIRECTORY`, which only systemd sets; a declared-but-missing directory fails closed rather than falling back. The two activation gates carry over unchanged: the shipped unit does not contain `--execute`, and only `install.sh --enable-execution` writes a drop-in that adds it, with `ExecStart=` cleared first because systemd appends to that directive and a drop-in that only added a line would run the monitor twice per firing. The health unit is denied every network address family and is given no credentials, so a future edit that gives the observer network access or secrets fails loudly. The watchdog timer is deliberately not `Persistent`, because a machine that was off must not replay monitoring runs it never made. Alternatives considered: a long-running daemon with an internal scheduler, rejected because a oneshot plus timer keeps the crash surface at one run and matches the Windows model; reading credentials from a root-only file, rejected as the plaintext-on-disk case the project exists to avoid; a `.deb` package, deferred until the units have run on a real host. Consequence: adding a writable path or a network need means editing a unit, which the suite notices. | The safety model is in the two gates and the least-privilege boundary, so both must be expressed in the unit files where a reviewer can see them, not in prose. |
| ADR-021 | 2026-07-27 | Approved | The local health observer's shared failure mode is accepted and documented rather than engineered away. It runs on the same host, under the same init system, from the same install as the watchdog, so it is independent of the watchdog's third-party dependencies and of its exit codes but not of a fault that prevents both from starting. That case occurred on 2026-07-27: one missing interpreter wedged both jobs, and the observer could not report the outage it exists to report. Alternatives considered: giving the health job a different start mechanism, rejected as adding a second mechanism to maintain while still sharing the host; an observer outside the host, rejected for now as a new moving part and an external dependency, while noting it is the only option that also covers the machine being off. Consequence: the limitation is stated in the Debian health unit, in `01_docs/DEBIAN.md` and in section 9 of the improvement plan, so nobody reads the health monitor as a guarantee it cannot give. | An accepted risk that is written down where the reader will meet it is worth more than an unwritten mitigation, and the alternative was to imply an independence the design does not have. |
| ADR-022 | 2026-07-28 | Approved | Configuration migration and validation have one implementation, `scripts/configure.py`, and `scripts/Migrate-LocalConfig.ps1` is a thin wrapper that calls it. It is standard-library only, because configuration work has to be possible before the environment exists, which is exactly when the third-party dependencies are not installed. `--validate` calls the monitor's own `validate_config` rather than restating the predicate, so a configuration that validates is one the monitor accepts. Migration fills missing keys from `config.example.json` for `monitor`, `outbox` and `health` only: `paths` and `router` carry placeholders in the template, and writing one of those over a working value would break a live install at its next run. `execution_mode` is added when absent and never changed when present, and Notion is never enabled without `--enable-notion`; a migration must not promote an install into production or turn on remote logging nobody asked for. Every mode is a dry run unless `--apply`, which writes a timestamped backup first. Alternatives considered: porting the PowerShell script to shell for Debian, rejected as a second implementation that would drift, which is the failure the shared defaults module already exists to prevent; a `.deb` postinst hook doing the migration, rejected because an unattended schema change to a file that decides whether a router gets restarted should be an operator's act. | The two platforms must agree on what a current configuration is, and the only reliable way to guarantee that is for there to be one answer rather than two that look alike. |
| ADR-023 | 2026-07-28 | Approved | A restart requires evidence, not the age of a marker. The decision is computed from the `runs` table, which already records every run and its connectivity result, and requires two independent conditions: the most recent successful run is at least `failure_minutes_before_reboot` old, and at least `monitor.required_failed_runs` failed runs fall inside `monitor.failure_window_minutes`. The first preserves the promise the notice and the event text make and breaks on flapping, because one successful run moves the reference forward. The second is what makes a gap in monitoring harmless: a sleeping machine, a logged-off user or a run that declined the lease contribute no observations, and history cannot satisfy a count taken over a recent window. `required_failed_runs` is floored at two in validation, so no configuration can restore the behaviour where one observation after a gap sufficed. `first_failure_utc` survives only to record whether an outage has been announced. Alternatives considered: requiring only a count within a window, rejected because three failures at five-minute spacing would fire after ten minutes and quietly weaken the documented fifteen; keeping the marker and ignoring it when stale, rejected as a second rule about the same fact when the run history is already the fact; a consecutive-failure counter in `state`, rejected as new state to keep correct when the runs table already holds the evidence. Consequence: the event detail and the notice state what was observed rather than a constant, and a monitoring gap delays a restart rather than causing one. | The property the project documents is fifteen minutes of observed unavailability. Deriving the decision from observations rather than from a derived marker makes the code enforce the property the documentation claims. |
| ADR-024 | 2026-07-28 | Approved | The Debian install owns what it installs: `deploy/debian/install.sh` places every file with `install -m 0644 -o root -g root` per file rather than `cp -a` on the source tree, and removes `${PREFIX}/src` first. `cp -a` preserves the ownership of the checkout, and the documented invocation is `sudo` from a user-owned clone, so the installed code ended up writable by an ordinary account while `systemd` ran it as the service user with the router credentials decrypted into the process. No unit directive prevents that, because none of them says anything about who may rewrite the code before it starts. The removal is separate: `install` overwrites the files it is given, so a module deleted upstream survived an upgrade and stayed importable. Alternatives considered: chown and chmod after `cp -a`, rejected because it leaves a window in which the files exist with the wrong owner and depends on a second command running; installing from a packaged artefact, deferred as the right answer for a real distribution but disproportionate for a script the owner runs by hand. Consequence: `04_tests/test_deploy.py` runs the installer verbatim at its real paths inside a throwaway mount namespace and observes the resulting modes, because ownership is a property of an install and cannot be read off the script. | Reading the script is how the defect survived review; the resulting file modes are the only evidence that settles it. |
| ADR-025 | 2026-07-28 | Approved | A `CREDENTIALS_DIRECTORY` is trusted only when it is owned by the run's own user with no group or other access, and the bootstrap error log follows `$LOGS_DIRECTORY` before any other candidate. The two are one decision about the same platform: on Debian the service account has no home directory and both units set `ProtectHome=yes`, so the previous home-directory fallback resolved somewhere unwritable, and `append_log` is called from inside the top-level exception handlers, so it raised over the original error and skipped the non-zero exit — the crash record was not merely misplaced, it was replaced by a permission error about where it would have gone. Both handlers now tolerate an `OSError` from recording. On the credential side, `systemd` decrypts credentials onto a private tmpfs owned by the service user with mode 0700, and that is the entire basis for treating the source as equivalent to a desktop keyring; accepting any directory would have let a plain directory of plaintext files satisfy this project's own fail-closed gate. Alternatives considered: requiring the path to live under `/run/credentials/`, rejected as an undocumented implementation detail of `systemd` that would break the moment it changed, where ownership and mode are the properties actually relied on; making the installer create a home directory for the service account, rejected because `ProtectHome=yes` is worth more than the convenience. Consequence: `install.sh --install` refuses when the service account cannot write its log directory, and the check is exercised behaviourally rather than by reading the script. | A monitor that cannot record a failure it hit before opening its database leaves nothing to read afterwards, and a credential store that is trusted on the sole evidence of being a directory is not a protected store. |
| ADR-026 | 2026-07-28 | Approved | A test that pins safety-relevant behaviour is not accepted until the behaviour has been reverted and the test observed to fail. The fourth review round found that removing the line that stamps an outage, the line that clears it, or the dry-run cooldown stamp left every suite green, so the suites were confirming their own fixtures; the same round found two checks in the health suite that scanned the source text for the word "reboot", which a health monitor spawning the watchdog with `--execute` would have passed while restarting the router. The rule that follows is that a pin is judged by what it catches, not by what it asserts. Where the property lives in a file rather than in a value - file ownership after an install, which command a scheduled task registers - the check is made against the parsed or executed artefact rather than against its text: the installer is run inside a throwaway mount namespace, `src/health.py` is examined through its abstract syntax tree, and `scripts/Install.ps1` through PowerShell's own parser. Alternatives considered: a coverage threshold, rejected because line coverage is satisfied by a test that executes a line without asserting anything about it, which is precisely the defect found; a mutation-testing tool, deferred rather than rejected - the reversion list is currently kept by hand in the working notes for each change, which does not scale but is honest about what was actually checked. Consequence: each change now carries a recorded list of reversions and the suite each one fails. | Four review rounds passed over pins that could not fail. The only evidence that a test protects something is that it breaks when the protection is removed. |
