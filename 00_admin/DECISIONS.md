# Decisions and assumptions

| ID | Date | Status | Decision or assumption | Rationale |
|---|---|---|---|---|
| ADR-001 | 2026-07-26 | Approved | Project logic is stored in the project root and operations logs/state use a separate, locally configured path outside the project tree. | Logs must remain available during an Internet outage. |
| ADR-002 | 2026-07-26 | Approved | Windows Credential Manager stores router and Notion secrets. | Secrets must not be stored in code, configuration files, or logs. |
| ADR-003 | 2026-07-26 | Approved | Router restart and Notion writes are allowed only with explicit `--execute`, every five minutes, after 15 continuous failure minutes and with a 30-minute cooldown. Authorization remains valid until revoked by the project owner. | Standing authorization under A1. The content of a Notion write is governed by ADR-014, which records that technical error detail is not minimized. |
| ADR-004 | 2026-07-26 | Superseded by ADR-010 | Tests, dry-run, and the current scheduled task must never request a router restart. | Independent safety boundary requested by the project owner. |
| ADR-005 | 2026-07-26 | Approved | The scheduled task runs only under the project owner's logged-in Windows account. | The same user profile can read Credential Manager and display a persistent restart notification. |
| ADR-006 | 2026-07-26 | Approved | Local SQLite logging is mandatory; Notion logging is an opt-in secondary destination. | Monitoring must preserve local operational evidence during Internet outages and must not depend on a remote integration. |
| ADR-007 | 2026-07-26 | Approved | ZenWiFi Monitor is published under Apache License 2.0 with David Hagdahl as the copyright owner. | The license permits broad reuse with an express patent grant and aligns with the Apache-2.0 router-library dependency. |
| ADR-008 | 2026-07-26 | Approved | Local configuration schema migrations are dry-run-first, create an ignored backup before writing, preserve TLS, and require an explicit opt-in for Notion logging. | Migration must not activate external behavior or silently change optional remote logging. |
| ADR-009 | 2026-07-26 | Approved | Public release uses an ignored, history-free `_public` staging tree generated only from a clean current source tree. | Earlier local Git history contains environment-specific and personal metadata that must never reach the public remote. |
| ADR-010 | 2026-07-27 | Approved | Production activation requires a separate owner decision, task registration with `-EnableExecution`, and local `execution_mode` set to `execute`. Tests and dry-run must never request a router restart. | The explicit task argument and local configuration are independent activation gates. |
| ADR-011 | 2026-07-27 | Approved | The project carries a single semantic version in the root `VERSION` file. Every tracked file except `LICENSE` and `VERSION` carries a `ZenWiFi Monitor version: MAJOR.MINOR.PATCH` marker in its native comment syntax; `config.example.json` carries it as a `config_version` key. `scripts/check_versions.py` verifies that all markers and the newest `CHANGELOG.md` release heading equal `VERSION`, and CI fails on drift. Alternatives considered: independent per-file versions, rejected because Git already provides per-file history and per-file counters drift silently; a project version plus per-file revision counters, rejected as unjustified maintenance for a single-maintainer project. Consequence: a release bumps `VERSION`, the CHANGELOG heading and every marker together. | The governing standard prescribes no versioning scheme for downstream projects, so the scheme is a project decision. A single version keeps the marker verifiable mechanically and mirrors how the standard marks its own documents. |
| ADR-012 | 2026-07-27 | Approved | Every scheduled ZenWiFi Monitor job is registered through `scripts/RouterWatchdog.vbs`, which launches the target script with window mode 0 and without waiting. The wrapper takes `--script=<entry point>` so additional jobs reuse one silent launcher, but only against a two-entry whitelist, `src\watchdog.py` and `src\health.py`; any other value, and any argument the wrapper does not recognise, exits 2 so Task Scheduler records the refusal and the wrapper cannot become a general silent runner for an arbitrary file, and `Install.ps1` refuses to report success unless the registered task action is `wscript.exe`. Notices are spawned through the windowless interpreter with `CREATE_NO_WINDOW`. The wrapper resolves the interpreter from `%LOCALAPPDATA%\ZenWiFiMonitor\.venv` first and the project tree second, and refuses rather than launching what is not there: exit 3 when no interpreter is found and exit 4 when the entry point is missing. Every refusal is also appended to the bootstrap error log, because an exit code alone is invisible unless somebody reads the task history. Alternatives considered: one wrapper per job, rejected as duplicated launch logic that drifts; registering `python.exe` directly, rejected because it raises a console window and breaks silent operation; calling `Run` without checking the paths first, rejected because `Run` in window mode 0 without waiting reports no error, so a missing interpreter leaves the job dead while Task Scheduler reports success. | An unattended job must raise no UI surface, steal no focus, and still leave a durable run marker. A single audited wrapper makes that property verifiable for every present and future job. |
| ADR-013 | 2026-07-27 | Approved | Notion delivery runs through a durable SQLite outbox: an event is committed locally before any remote call and marked delivered only after a successful response; undelivered events are sent oldest first and delivery stops on the first failure. Retries are bounded per event and per run, delivered events are purged after a retention window, and persisted error detail is sanitized so no authorization header is stored. A separate standard-library health monitor runs on its own fifteen-minute silent task, reports a stale run, an unreadable database, a changed bootstrap log and a stalled outbox, notifies only on a new or escalating unhealthy state, and can never restart the router. Bootstrap logging is size-bounded with rotation before write. Alternatives considered: delivering inline at event creation, rejected because an outage is exactly when the remote call cannot succeed; unbounded retry, rejected because one poison event would block the queue forever. | Local operational evidence must survive an outage and reach Notion afterwards at least once, and silent monitoring needs an independent observer that does not share the watchdog's dependencies. Delivery is deliberately at-least-once rather than exactly-once: a run interrupted between a successful response and the delivered mark resends the event, which is preferred over dropping it. |
| ADR-014 | 2026-07-27 | Approved | Technical error detail delivered to Notion is not content-minimized. An `Error` event carries the unmodified exception text, which can include the router endpoint and other environment data. The project owner accepts this because the configured Notion data source is a private surface reachable only by the owner's own integration, and because the alternative, discarding error text, would remove the evidence the remote log exists to preserve. Credentials remain excluded: no token, password or authorization header is ever placed in an event. Alternatives considered: a fixed error template with only the exception class, rejected as losing the diagnostic value; local-only error events, rejected because a failed restart is exactly the event worth mirroring. Consequence: an operator pointing this project at a shared or team Notion database inherits a different risk and should minimize the detail first. | The risk depends on who can read the destination, and the owner's destination is private. Recording the acceptance keeps the documented data classification honest. |
| ADR-015 | 2026-07-27 | Approved | The repository deviates from the standard's B9 tree. Source lives in `src/` and `scripts/` rather than `03_src/modules` and `03_src/scripts`, and `02_data/`, `05_logs/` and `06_exports/` do not exist. B9 states that the structure shall be adapted to the project type and that any deviation is recorded here. This project is a single-purpose watchdog with three source modules and no data pipeline: it ingests nothing, produces no exports, and writes its only persistent state to a SQLite database and log directory that ADR-001 deliberately places outside the project tree so they survive an outage. Creating empty `02_data/`, `05_logs/` and `06_exports/` directories would therefore describe a pipeline that does not exist and would invite writable runtime data back into a cloud-synced tree. Alternatives considered: adopting the full tree, rejected for the reasons above; renaming `src/` to `03_src/` alone, rejected because it would break the registered scheduled task's launcher path and every documented command for a purely cosmetic gain, with no `03_src/modules` split to justify it at three modules. Consequence: a contributor arriving from the standard will not find the numbered source directory; `01_docs/ARCHITECTURE.md` carries the mapping, the edit status per directory and the logic/data classification. Revisit if the project grows a data pipeline or a fourth source module. | The layout is verified against an actual filesystem inventory rather than a template, and the deviation is deliberate and bounded rather than accidental drift. |
| ADR-016 | 2026-07-27 | Approved | The Python environment the scheduled jobs use lives at `%LOCALAPPDATA%\ZenWiFiMonitor\.venv`, beside the bootstrap log, not in the project tree. The project tree is cloud-synced, and a sync or folder-hygiene routine moved the project-local `.venv` out from under the running jobs, after which the launcher called `Run` on a path that no longer existed; the job died while Task Scheduler reported success, and the first failure left an invisible script-host dialog that wedged the task so every later run was refused by the single-instance policy. A project-local environment remains supported as a fallback for development. Alternatives considered: keeping the environment in the project and excluding it from sync, rejected because it depends on a setting outside this project that no test can assert; moving the whole repository off the synced drive, rejected as a larger change than the failure requires and still leaving the environment inside a working tree that gets cleaned. Consequence: `Install.ps1 -InstallDependencies` creates the environment in the runtime location, and the documented commands name it. | This is the same reasoning ADR-001 applies to the database and the logs: state an unattended job depends on must not live where another tool may move it. |
| ADR-017 | 2026-07-27 | Approved | Dependencies are locked by hash, not only by version. `requirements.in` names the direct dependencies and is the only file edited by hand; `requirements.lock.txt` is the generated, fully resolved output carrying every transitive distribution with its hashes, and is installed with `--require-hashes` so pip refuses the entire set unless every artefact matches. One file covers both supported platforms through environment markers rather than a file per platform. GitHub Actions are pinned to immutable commit hashes with the upstream release name recorded beside each. Alternatives considered: version pins alone, rejected because a version pin does not detect a substituted artefact; a lock file per platform, rejected as two files that drift; leaving actions on moving tags, rejected because a retagged release enters the build silently. Consequence: adding or upgrading a dependency means regenerating the lock file and committing input and output together. | An unattended job that can restart a router should fail its install rather than run an artefact nobody verified. |
